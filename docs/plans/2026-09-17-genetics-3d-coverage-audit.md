# 遗传结果与 3D 素材覆盖评估

状态：代码核对与可执行探针完成；下列匹配策略、补素材优先级是建议，尚未实现。用户已认可 11 套样板美术。基于 `6684823`；本轮不改遗传算法、不新增生成任务、不接正式主图。

## 与总纲关系

承接 09-16 产品后续计划的主图接入第 1 步，以及 09-17 七套贴图制作。当前五位点视觉接入不依赖全部 v2；全白等新能力必须先完成总纲阶段 2（观察 / 潜在基因型 / 表达表型、个体上下文、证据等级），再推进阶段 3。旧总纲中的生物学论据本轮未重新作外部文献审查，不能把计划条目当成已验证的当前科学契约。

## 当前真实能力

- `src/genetics/phenotype.ts`：色系 orange / black / tortie，稀释、虎斑有无、白斑 0–4、长短毛。橘色系规范化为 tabby=true。
- 归一化外观有 100 种：10 个底色/纹路组合 × 5 档白斑 × 2 档毛长；短毛 50、长毛 50。不是 100 个品种，也不是发生频率分布。
- `loci.ts` / `solve.ts`：现有 O、D、A、S、L 五位点；有父母合法配对集合与联合筛选。新位点、品种上下文、分层观察契约尚未实现。
- `illustration/spec.ts`、`pixels.ts`、`browser.ts`：2D 能按上述字段组合，使用长短毛底稿、条纹、玳瑁斑块和递增白斑遮罩；它也只是当前模型的示意图，不是任意真实猫照片复原。
- `punnett.ts` 去重后返回“可能有哪些”，不保留配子组合的重复次数。没有完整正推概率 API；不能用结果条数倒数当发生概率。

## 11 套模型逐项决策

所有模型均为短毛同一体型、固定整张贴图、固定眼鼻耳颜色。眼色和真实斑块位置当前不是引擎输入，也不代表遗传预测。以下为候选适用条件，需在正式匹配表中显式登记。

| 模型 | 候选表型 | 当前决策 |
|---|---|---|
| 纯黑 | black / 非稀释 / 无虎斑 / white=0 | 可作为首批匹配候选 |
| 纯蓝灰 | black / 稀释 / 无虎斑 / white=0 | 可作为首批匹配候选，不能由蓝色推出英短 |
| 狸花 | black / 非稀释 / 虎斑 / white=0 | 可作为首批候选；只代表虎斑示意，不代表可推导具体纹型 |
| 蓝狸花 | black / 稀释 / 虎斑 / white=0 | 同上 |
| 玳瑁 | tortie / 非稀释 / 黑色部分无虎斑 / white=0 | 可作为首批候选；橘色区域有纹理不等于黑色部分有虎斑 |
| 橘猫 | orange / 非稀释 / 虎斑 | 胸腹浅色须与 2D 无白、带白档并排校准，不能仅凭名字当 white=0 |
| 奶油 | orange / 稀释 / 虎斑 | 同上 |
| 黑白 | black / 非稀释 / 无虎斑 / 带白 | 白胸白袜不等于“约一半白”；先确认对应白斑档，不能覆盖所有 white>0 |
| 蓝白 | black / 稀释 / 无虎斑 / 带白 | 同上；与黑白的白鼻口不同，不要求斑块形状完全一致，但需明确典型档 |
| 三花 | tortie / 非稀释 / 黑色部分无虎斑 / 带白 | 白斑档待校准，不可替代虎斑三花 |
| 淡三花 | tortie / 稀释 / 黑色部分无虎斑 / 带白 | 同上 |

美术认可与字段覆盖认可是两件事。首批明确候选是 5 个无白短毛状态；另 6 套须校准，不能宣称 11/100 已严格覆盖。状态覆盖率也不是用户使用率。固定素材不因名字相同覆盖多档白斑；同档允许典型斑块位置差异，须说明“外观示意”。

## 缺素材：新增还是回退

| 缺项 | 是否已能计算/2D 展示 | 建议 | 理由 |
|---|---|---|---|
| 淡玳瑁，无白短毛 | 是 | 第一批补 1 套贴图 | 补齐现有玳瑁浓淡对，CANON 已有该条目 |
| 橘白、奶油白，短毛典型白斑 | 是 | 第一批候选 2 套 | 橘白已有快捷入口；须先确认现有橘/奶油是否已经能承担该档，避免重复生成 |
| 狸花白、蓝狸花白，短毛典型白斑 | 是 | 第一批补 2 套 | 狸花白已有快捷入口，缺的是贴图而不是遗传能力 |
| 玳瑁虎斑、淡玳瑁虎斑，以及带白版本 | 是，但结果分组会丢变体 | 先 2D，后补专用贴图 | 先保留黑色部分有无虎斑的语义，再做对应素材 |
| 零星白、大部分白、几乎全白 | 主体可选，2D 可画；后代量级有简化 | 先 2D | 一张整贴图不能精确适配多档白斑；不要为每个状态立即生成一套 |
| 所有长毛 | 是 | 先 2D，后单独验证一套长毛几何 | 当前短毛 GLB 换色无法长出饰毛/蓬松尾巴，不应复制 50 套纹理冒充支持 |
| 全白、重点色、银色、巧克力等 | 当前契约不支持 | 标为未支持，另开引擎扩展 | 现有 2D 也不能正确兜底；不能造一个 CoatSpec 冒充这些花色 |

优先新增最多 5 套贴图，不是立刻生成的授权任务；每套验收包含正侧背与白斑档，质量不过则仍回退。先利用已校准素材，缺资产时 2D 是长期有效的支持路径。

## 引擎 / 结果投影缺口（本轮代码确认）

### P0 接入前：名称合并丢失外观变体

`children.ts:83–84` 按 `coatName()` 去重，仅保留第一个 spec。`naming.ts` 把所有 white>=2 的玳瑁都叫“三花/淡三花”，不保留虎斑差异；普通系列 white=2/3 也常同名。因此名字不能作素材键，现有 `r.specs[name]` 也不能代表全部后代变体。

实测输入：非稀释、虎斑、white=2、短毛、黑色系母猫 × `MATES[2]` 橘猫。结果只有一个“三花猫”条目，代表 spec.tabby=true；但双方 A 的可能集合也能产生 aa，对应 tabby=false。这是确定的表示信息丢失，不是本轮新增算法 bug，也不等于名字本身错误。

建议保留一张花色卡片的交互，新增 `variants` / 结构化表型键，存完整变体与代表图身份；名称只用于显示。不要重新录制冻结 golden 掩盖变化。针对上述输入写独立回归，旧 API 若需兼容可保留 representative spec。

### P0 接入前：后代白斑量级不是确定预测

`loci.ts` 中 white=1、2、3、4 都约束到 {Ss,SS}；探针结果完全一致。但 `children.ts:75` 为画图使用 `ss→0, Ss→2, SS→3`，没有表达白斑量级的不确定性。不可把代表图转成“遗传精确预测半白/大部分白”，更不能据此倒推原猫的 S 型。

建议先区分“有白/无白的可能性”和“示意图白斑档”；后代结果附带量级未确定标记。只有确定的观察输入才能走严格档位素材匹配。改投影与说明，不把绘图用 SW 表作为新的科学规则。

### 已有但不是缺失：长短毛结果合并

后代可同时有长短毛时，当前一张短毛代表图＋顶部“两者都可能”；必然长毛才画长毛。此前明确选过不把卡片数量翻倍。保持该交互，但后代主图/详情必须携带毛长可能集，不能由 representative.long=false 宣称只可能短毛。

### P1 产品目录不完整

`CANON` 有 16 条，命名器还有 10 个名字不在目录：高白黑、高白狸花、高白蓝、蓝虎斑白、高白蓝虎斑、高白橘、奶油白、高白奶油、玳瑁虎斑、淡玳瑁虎斑（均带“猫”后缀）。不是这十种算不出来，而是不能从该目录完整选择。

配偶 `MATES` 只有 6 条、每次露出 5 条，蓝猫/奶油/蓝白等未提供配偶入口；底层接受 CanonEntry，不能误判为 D 位点不能算。建议数据目录统一后再扩 UI，无需先新增基因。

### P2 总纲尚未落地的能力

- 观察值 / 潜在基因型 / 表达表型三层契约、每只猫自己的品种/未知/混种上下文、证据等级门控。
- KIT 全白扩展、重点色 C、黑色系扩展 B、银色 I、具体虎斑纹型、CORIN 等：本轮确认没有对应实现；旧计划需开工时逐项重审证据和范围。
- 精确概率和显性携带假设控制尚未实现。现有 certain/maybe 文案等级不等于生物学证据等级机制。
- 总纲阶段 1 旧的长毛、联合配对和列表截断修复不可重新列成当前待做项；已有实现保留。

## 实施建议与验收闸门

1. 先新增独立素材匹配契约：按色系、稀释、虎斑、白斑、毛长查表；返回 asset / 2D(reason) / unmodeled(reason)，不做名字近似匹配。补素材前先校准 6 套待定资产。
2. 修正后代投影的变体丢失与白斑/毛长不确定性表达，保留当前卡片分组交互。主体输入的匹配可独立开发，不必等所有 v2 位点。
3. 用归一化 100 状态做穷举匹配检查；无资产、长毛、不同白档、玳瑁虎斑不能误命中；未知能力不伪装成已有 2D 支持。针对模型失败/快速切换另做集成验证。
4. 再按上表补最多 5 套候选贴图。补完不宣称覆盖所有田园猫；记录每套固定档位及不可表达项。
5. 正式主图接入另需解决发布方式。当前 AGENTS 仍要求单文件离线交付，上一轮提出的独立模型文件/CDN 只是建议，尚未取代约定。本轮不改打包方式。

## 补充：全量 3D 的制作与网页成本（09-17）

### 范围与积分

“当前模型全部”是短毛 50 / 长短毛合计 100 个规范化外观状态；“真实田园猫所有花色纹路”还包含当前不支持的能力及任意斑块分布，没有这个固定上限。应定义典型预设全覆盖，不承诺每只真实猫都复原。

沿用独立 GLB 的直观方案，若现有 11 套都能各覆盖一档，短毛还需至少 39 套，全量还需至少 89 套；白斑校准可能增加重做，长毛另需新几何。以下仅以已经发生的大陆版制作流水估算，不是当前套餐报价：副本 5 + 初次贴图 20，每次重试再 20。七套实花 215，平均约 30.7。

| 新增规模 | 首次都成功，25/套 | 每套额外重做两次，65/套 |
|---|---:|---:|
| 短毛新增 39 套 | 975 积分 | 2535 积分 |
| 长短毛新增 89 套 | 2225 积分 | 5785 积分 |

不包含新长毛几何、参考图、源文件整理、生成失败、后续规则修改；不是消费上限。暂不能按曾看到的月费直接换算人民币，需订阅实际额度/导出规则。若仅为排期假设，每套主动检查与整理 15–30 分钟，39 套约 10–20 小时，89 套约 22–45 小时；不含生成等待、返工、共用模型改造与长毛造型验收，不是工期承诺。主要风险是眼鼻耳、白斑边界、正侧背和切面风格不一致。

### 本地文件实测

读取 11 个轻量 GLB 的文件长度和内嵌 image bufferView：总计 30,471,232 字节，平均 2,770,112 字节；内嵌图片约 0.315–0.546 MB，其余模型/元数据约 2.366–2.376 MB。MB 按十进制；未包含 HTTP 传输压缩。

不做共享时，50 套约 138.5 MB，100 套约 277 MB，是整个资产库大小，不是首屏必下流量。当前每只约 8 万三角面；屏幕只显示一只时，三角面不会因库存变成 100 倍。

比对首个 mesh primitive 的 POSITION / NORMAL / TEXCOORD_0 / indices 对应 bufferView 哈希：奶油、蓝狸花、蓝白、淡三花、玳瑁五套一致；纯黑与纯蓝灰一致；狸花与黑白一致。其余两套不同。说明部分现有资源具备共享候选条件，但不是全部 11 套已经可直接换图；还需验证材质参数、节点变换和渲染。不同 UV 不可硬套纹理。

若标准化为长短毛各一个约 2.37 MB 的共享身体，各状态保留约 0.3–0.55 MB 贴图，100 状态的库体积粗估 35–60 MB。这是架构估算，尚未实现；材质压缩、法线共享、纹理烘焙结果会改变数值。

### 加载与内存方案

- 首屏仅取当前猫：目前量级约 2.7 MB 模型，另加页面、脚本和 2D 占位。20 Mbps 下该模型纯传输约 1.1 秒，5 Mbps 约 4.4 秒；均排除延迟、解码、首次上传 GPU，不是实测加载时间。
- 同身体换色按需取贴图，目标沿用现有图片体积约 0.3–0.55 MB；跨毛长才换身体。只预取少量相邻选项，不预取全库。
- 小卡片用静态缩略图；一个活动 3D 场景，释放不再使用的纹理，控制 GPU 缓存；浏览器磁盘缓存不等于显存常驻。
- JPEG 小不代表显存小：按 RGBA8 + mipmaps 估算，一张 2048² 纹理约 21.3 MiB，2–3 张约 43–64 MiB，仅纹理，不含其他渲染资源。不能全量常驻。可试 KTX2 和网格压缩，收益需实测。
- 显存为按纹理尺寸推算，未作 GPU 实测。压缩接入参考已核实的 Three.js 官方 GLTFLoader 文档 https://threejs.org/docs/pages/GLTFLoader.html 。
- 单文件离线产物若嵌入全库不能依赖按需请求减小下载量；独立模型资源发布仍是待确认方案，未修改 AGENTS。

建议先在现有五套兼容模型中验证“共享身体＋独立贴图”，测实际加载和手机表现，再决定全量制作。保留 AI 独立贴图的已认可外观，不先押注未经验证的程序化任意花纹；后者虽能减少文件数量，却可能重现之前换色效果不满意的问题。
